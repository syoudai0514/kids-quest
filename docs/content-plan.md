## 2. 設計原則（全WP共通）

1. **事実の正確性が最優先。** 出典は学習指導要領・教科書準拠。曖昧な問題は入れない。
2. **1問1論点。** 複数の知識を同時に問わない。
3. **選択肢の設計:**
   - 正解だけが長い／短いという見た目の手がかりを作らない（`doutoku.js` の `longestWrong` 方式を全教科へ横展開）
   - ダミーは**よくある誤り**を反映する（乱数のズレだけにしない）
   - 選択肢間で表記・絵文字が重複しない（既存 `makeChoices` の保証を維持）
4. **`explain` は必ず「なぜ」を含む。** 答えの言い換えは禁止（例: 「これは『ほし』。ほしだよ」は不可）。
5. **既存の進級台帳（`unitLedger`）を壊さない。** 単元追加時は `NUMBERS_KINDS_BY_GRADE` 等の公開配列を必ず同時更新する（`verify-learning-integrity` が「出るのに必須でない／必須だが出ない」を検出する）。
6. **既存セーブを壊さない。** `itemKey` の意味を変更しない。新規は新しいキー空間を使う。

## 4. Phase 2 — 「むずかしいモード」（中学受験レベル）

### 4.1 モードの定義

| モード | 対象 | 内容 |
|---|---|---|
| **ふつう**（既定） | 全学年 | 現行＝学習指導要領準拠 |
| **むずかしい** | 全学年 | 小4-6: **中学受験レベル**（特殊算・読解・受験理社）<br>年長-小3: **思考力・先取り**（規則性・図形パズル・文章題） |

> 年長〜小3に中学受験そのものを課すのは不適切。低学年のむずかしいモードは「1〜2学年先取り＋思考力問題」と定義する。

### 4.2 アーキテクチャ設計 ⚙️（WP9・他WPの前提）

#### (a) モードの保持場所
```js
// src/state/GameContext.jsx  createInitialState().settings
settings: { ..., mode: 'normal' }   // 'normal' | 'hard'
```
- `settings` はプロフィールごとに保存され、`settingsForCurrentVersion()` が fresh を先に展開するため**既存セーブには自動で `'normal'` が入る**（マイグレーション不要）。
- 保護者画面（`ParentScreen.jsx`）にトグルを追加。子ども側からは変更不可。

#### (b) 問題生成への伝搬
```js
// src/screens/ActivityPlayer.jsx  makeQuestion() の params に追加
mode: stateRef.current.settings?.mode || 'normal'
```
同様に `FreeStudyScreen` / `ReviewScreen`（→ ActivityPlayer 経由なので自動）/ `trialQuestions.js` にも渡す。

#### (c) ファイル構成
既存ファイルの肥大化を避け、**モード別に分離**する:
```
src/data/content/
  numbers.js          … ふつう（既存）
  hard/
    numbers-hard.js   … export const HARD_BUILDERS, HARD_KINDS_BY_GRADE
    reading-hard.js
    rika-hard.js
    shakai-hard.js
    english-hard.js
```
各ドメインの `generateXQuestion` 冒頭で分岐:
```js
if (params.mode === 'hard') {
  const q = generateHardQuestion(params, reviewKey)
  if (q) return q          // 該当が無ければ ふつう へフォールバック
}
```

#### (d) itemKey / 単元の名前空間（**最重要**）
- 中学受験専用の出題タイプは **`n:jrXxx`** のように `jr` 接頭辞を付ける（例: `n:jrTsurukame`）。
- これにより `unitIdFor()` は `math:jrTsurukame` を返すが、`NUMBERS_KINDS_BY_GRADE` に載せなければ **`unitLedger` に入らない＝進級要件にならない**。
- **原則: むずかしいモードは進級判定（ほしのしれん）を変えない。** 難しい問題を解けないと進級できない、という状態を作らない。
- `isNumbersReviewStale()` は `KIND_HOME_GRADE` に無いキーを `false`（除外しない）で返すため、追加対応不要。
- ふつうモードに対応単元がある場合（例: hard版の分数のわり算）は `unitId: 'math:fracDiv'` を明示的に付けて既存単元に合流させてよい。

#### (e) 解説の強化（**中学受験モードの本体価値**）
現行の `explain`（1文）+ `explainColumn`（筆算）に加えて、**段階解説** を追加する:
```js
{
  explain: '…結論と方針（1文）',
  explainSteps: [                       // 新規
    'つるの数を□とすると、かめは (10-□) 匹',
    '足の合計 2×□ + 4×(10-□) = 32',
    '式を整理すると □ = 4'
  ],
  explainColumn: '…筆算や図（任意）',
  explainWhy: '全部つるだと仮定すると…という考え方（別解・本質）'  // 新規・任意
}
```
UI 側（`ActivityPlayer.jsx` の `.explain-card`）に `explainSteps` の番号付きリスト表示を追加。CSS も併せて拡張。

#### (f) 影響させない範囲
- バトル・チケット・XP・図鑑・そうびの報酬設計は**一切変更しない**
- ほしのしれん（章末テスト）は**ふつうモードの問題で実施**（進級の公平性のため）
- SRS の間隔設定は共通

## 6. 検証計画（WP11）

### 6.1 新規アサーション（`scripts/verify-content.mjs` 拡張）

```
□ 漢字が学年別配当表と完全一致（1026字、学年ごとの字も一致）
□ 熟語は「その学年までの配当漢字」だけで構成されている
□ 各学年の各単元から必ず1問以上生成できる（既存の整合性テストを全単元へ）
□ 全問題が explain を持つ（空文字禁止）
□ explain が答えの単純な言い換えでない（正解文字列と完全一致でない）
□ 選択肢に重複が無い／正解は必ず1つ
□ 正解が「常に最長／最短」になっていない（全問題で分布を検査）
□ むずかしいモード: 全 hard ビルダーが全対象学年で生成でき、explainSteps を持つ
□ むずかしいモードの unitId が unitLedger を汚染していない（進級要件が変わらない）
```

### 6.2 表記チェック（新規・価値が高い）

```
□ 問題文・選択肢・解説に、その学年までの配当漢字以外が使われていない
   （使う場合はふりがな相当の配慮があること）
□ 逆に、小4以上でひらがなだらけになっていない（漢字使用率の下限チェック）
```

### 6.3 既存テスト
`npm run check`（content / english / learning-integrity / tts-cache / build）が全通過すること。

### 6.4 実機確認
各学年×各教科で実際に出題し、**学年不相応な問題が出ないこと**を目視確認（今回の「小6に九九」のような事故の再発防止）。

## 8. GPT レビューで意見が欲しい論点

### ① 中学受験レベルの「深さ」の設定
最難関（御三家・灘）水準まで踏み込むか、標準的な中堅校水準に留めるか。
現時点の提案は**中堅校〜難関校の標準問題**（ニュートン算・立体切断などの最上位は除外）。
対象児が現在5歳であることを踏まえ、まず小4-6の土台を厚くする方針でよいか。

### ② 4択という出題形式の限界
中学受験算数は本来「式を立てて記述する」学習。4択では**選択肢から逆算する解き方**が身についてしまう恐れがある。
- 案A: 現行の4択を維持し、解説を厚くすることで補う
- 案B: 数値入力（既存の `keypad` 型）を中学受験モードの標準にする ← **推奨**
- 案C: 途中式を選ばせる2段階問題（設問→式選択→答え）

### ③ 道徳「生命・死」の扱い（要判断）
ユーザーから「人の死とは、のようなことも学年に応じて扱うべき」という指摘があった。一方で:
- 現行の**3択クイズ形式は生命観を問うのに構造的に不向き**（正解を1つに決められない）
- 5歳の子が同じアプリを使う（学年を戻す機能もある）ため、**表示範囲の制御が必要**

提案する選択肢:
- 案A: 高学年のD視点は「**答えの無い問い**」形式を新設（選択肢に正誤を付けず、選んだ後に複数の視点を提示。SRS対象外）← **推奨**
- 案B: 事実ベースに留める（いのちは一つ・かけがえがない・受け継がれてきた）
- 案C: 生命の終わりに関する話題は保護者設定で明示的にONにしたときだけ出す

### ④ 漢字497字の入力方法
手作業で書くとミスが混入する。
- 案A: 配当表を人手で全入力＋検証スクリプトで突合
- 案B: 既存のオープンデータ（教育漢字リスト）を取り込み、読みだけ人手で調整 ← **推奨**
どちらにせよ**読み（yomi）の質**が肝で、機械的な音読み羅列にならないよう注意が必要。

### ⑤ ファイル分割の是非
`numbers.js` は既に1025行、`reading.js` は463行。今回の追加でそれぞれ3〜5倍になる。
ディレクトリ分割（`content/numbers/` 等）を推奨するが、**既存の import パスを壊さない**よう index を置く方式でよいか。

### ⑥ 学習量のバランス
1タスク4-5問・1日コア5タスク（約15分）という現行設計は、コンテンツが5倍になっても変えない想定。
「天才にしたい」という目的に対し、**1日の学習量そのものを増やす**設計変更（例: むずかしいモードでは1タスク8問）も検討すべきか。
