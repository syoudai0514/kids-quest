## 2. 設計原則（全WP共通）

1. **事実の正確性が最優先。** 出典は学習指導要領・教科書準拠。曖昧な問題は入れない。
2. **1問1論点。** 複数の知識を同時に問わない。
3. **選択肢の設計:**
   - 正解だけが長い／短いという見た目の手がかりを作らない（`doutoku.js` の `longestWrong` 方式を全教科へ横展開）
   - ダミーは**よくある誤り**を反映する（乱数のズレだけにしない）
   - 選択肢間で表記・絵文字が重複しない（既存 `makeChoices` の保証を維持）
4. **`explain` は必ず「なぜ」を含む。** 答えの言い換えは禁止（例: 「これは『ほし』。ほしだよ」は不可）。
5. **IDの責務を分離する。** `knowledgeId`（学習項目）、`unitId/skillId`（単元）、`questionInstanceId`（今回の数値・問題文・選択肢）を混用しない。指定復習と保存は `knowledgeId`、進級は `unitId/skillId`、同一問題再出題は `questionInstanceId` を使う。
6. **収録量と進級条件を分離する。** 全収録単元を学習対象に含める一方、問題バンクの1問・漢字1字を無条件に1進級要件へ変換しない。単元内の異なる項目経験数・別日回数・正答条件で評価し、追加前後の想定進級日数を比較する。
7. **未学習を優先する。** 通常出題は原則「指定復習・誤答再出題」→「期限到来SRS」→「未出knowledgeId」→「既習ランダム」の優先順位とし、大量追加した教材が出題されない状態を防ぐ。
8. **通常とhardの学習記録を分離する。** hardの正誤・SRS・習熟度は通常の `unitLedger`、ほしのしれん、週間必須数に混ぜない。通常単元と題材が同じでも自動合流は禁止する。
9. **既存の進級台帳（`unitLedger`）を壊さない。** 単元追加時は `NUMBERS_KINDS_BY_GRADE` 等の公開配列を同時更新し、出題可能性と必須条件を検証する。
10. **既存セーブを壊さない。** `itemKey` の意味を変更しない。新規は新しいキー空間を使い、保存移行後もXP・図鑑・装備・英語進捗・SRS・連続記録を保持する。

### WP6: どうとくの3段階化＋D視点 🔴

**対象**: `src/data/content/doutoku.js`

1. `BANK` を `low`（年長-小2）/ `mid`（小3-4）/ `high`（小5-6）の**3段階**に再編。

3. **目標量**: 各段階20問以上（現状 10/12）。

#### WP6-a: 「答えのない問い」形式の新設

D視点は一つの価値観を正解にできないため、専用形式を追加する（§8-④の決定）。

- 選択肢に正誤を付けず、選んだあとに**複数の見方**を提示する
- **正答率・SRS・習熟度・進級条件のすべてで対象外**（`recordUnitResult` は `doutoku` を既に除外済み。加えて `ANSWER` ディスパッチでこの形式を集計しないこと）
- 「まちがい」の演出・効果音を出さない（`ActivityPlayer` の feedback 分岐を追加）

#### WP6-b: 生命の終わりの扱い — **決定済み・厳守事項**

| 項目 | 決定 |
|---|---|
| 扱う範囲 | **生き物（虫・ペット・植物）の死まで**。**人の死は扱わない** |
| 対象学年 | **高学年（小5・小6）のみ** |
| 表示条件 | **保護者設定を必須**（`settings.showLifeEndTopics`、既定 `false`）。ONにしない限り一切出さない |

実装上の必須事項:

- 学年判定は **`state.grade`（現在の学年）** で行う。`gradeMax` で判定しないこと。
  **理由**: 保護者が学年を下げる機能（`LOWER_GRADE_MAX`）があるため、小6から年長へ戻した子に高学年向けの話題が出てはいけない。
- 設定OFF、または小4以下のときは、**この分類の問題を生成候補から完全に除外**する（出したうえで隠す、ではない）。
- 表現ガイド:
  - 死の具体的・視覚的な描写をしない
  - 恐怖や罪悪感をあおらない（「世話をしなかったから死んだ」等の因果を子に負わせない）
  - 「かなしい気持ちになってもいい」ことを肯定する
  - 宗教的・断定的な死生観を示さない
  - 正解を1つに決めない（WP6-a形式でのみ扱う）

### 4.2 アーキテクチャ設計 ⚙️（Phase 2 着手時に参照。**先行実装しない**）

#### (a) モードの保持場所
```js
// src/state/GameContext.jsx  createInitialState().settings
settings: { ..., mode: 'normal' }   // 'normal' | 'hard'
```
- `settings` はプロフィールごとに保存され、`settingsForCurrentVersion()` が fresh を先に展開するため**既存セーブには自動で `'normal'` が入る**（マイグレーション不要）。
- 保護者画面（`ParentScreen.jsx`）にトグルを追加。子ども側からは変更不可。

#### (b) 問題生成への伝搬
```js
// src/screens/ActivityPlayer.jsx  makeQuestion() の params に追加
mode: stateRef.current.settings?.mode || 'normal'
```
同様に `FreeStudyScreen` / `ReviewScreen`（→ ActivityPlayer 経由なので自動）/ `trialQuestions.js` にも渡す。

#### (c) ファイル構成
既存ファイルの肥大化を避け、**モード別に分離**する:
```
src/data/content/
  numbers.js          … ふつう（既存）
  hard/
    numbers-hard.js   … export const HARD_BUILDERS, HARD_KINDS_BY_GRADE
    reading-hard.js
    rika-hard.js
    shakai-hard.js
    english-hard.js
```
各ドメインの `generateXQuestion` 冒頭で分岐:
```js
if (params.mode === 'hard') {
  const q = generateHardQuestion(params, reviewKey)
  if (q) return q          // 該当が無ければ ふつう へフォールバック
}
```

#### (d) itemKey / 単元の名前空間（**最重要**）
- 中学受験専用の出題タイプは **`hard:n:jrXxx`** のようにhard専用名前空間を付ける（例: `hard:n:jrTsurukame`）。
- hard専用の `knowledgeId`、`unitId`、SRS台帳を使い、通常の `unitLedger` と保存キーを共有しない。
- **むずかしいモードは進級判定（ほしのしれん）を変えない。** 難しい問題を解けないと進級できない状態を作らない。
- 通常単元と題材が同じ場合（例: hard版の分数のわり算）も、通常の `unitId: 'math:fracDiv'` へ自動合流させない。hard側の成績は参考記録として独立保存する。
- `isNumbersReviewStale()` 任せにせず、hard記録が通常SRSの期限到来件数・習熟率・ホームメーターへ入らないことをテストで保証する。

#### (e) 解説の強化（**中学受験モードの本体価値**）
現行の `explain`（1文）+ `explainColumn`（筆算）に加えて、**段階解説** を追加する:
```js
{
  explain: '…結論と方針（1文）',
  explainSteps: [                       // 新規
    'つるの数を□とすると、かめは (10-□) 匹',
    '足の合計 2×□ + 4×(10-□) = 32',
    '式を整理すると □ = 4'
  ],
  explainColumn: '…筆算や図（任意）',
  explainWhy: '全部つるだと仮定すると…という考え方（別解・本質）'  // 新規・任意
}
```
UI 側（`ActivityPlayer.jsx` の `.explain-card`）に `explainSteps` の番号付きリスト表示を追加。CSS も併せて拡張。

#### (f) 影響させない範囲
- バトル・チケット・XP・図鑑・そうびの報酬設計は**一切変更しない**
- ほしのしれん（章末テスト）は**ふつうモードの問題で実施**（進級の公平性のため）
- SRS の間隔設定は共通

## 8. GPT/Codexレビュー反映後の決定事項・保留事項

### ① 実装優先順位 — 決定

普通モードの不足8項目を先に直す。むずかしいモードは普通モードの実装・保存移行・進級日数・実機確認が終わるまで開始しない。

### ② むずかしいモードの深さ — 決定

初期リリースは**中堅校〜難関校の標準問題**までとし、ニュートン算・立体切断などの最上位問題は除外する。低学年は中学受験問題ではなく、1〜2学年先取りと規則性・図形・条件整理を扱う。

### ③ 4択の限界 — 決定

算数のhardは数値入力を標準とする。途中式の理解が必要な問題だけ「式を選ぶ→答えを入力」の2段階にする。選択肢からの逆算だけで正解できる4択を主形式にしない。

### ④ 道徳D視点 — **決定（保留なし）**

- 生命尊重・自然愛護・感動と畏敬は低・中・高の全段階へ追加する。
- 一つの価値観を正解にする3択ではなく、選択後に複数の見方を示す「答えのない問い」形式を新設する（WP6-a）。
- この形式は正答率、SRS、習熟度、進級条件の対象外とする。
- **生命の終わりの扱いはユーザー判断により以下で確定した（2026-08-12）。実装詳細は WP6-b を参照:**
  - 範囲は **生き物（虫・ペット・植物）の死まで。人の死は扱わない**
  - 対象は **高学年（小5・小6）のみ**
  - **保護者設定を必須**とし、既定はOFF（`settings.showLifeEndTopics = false`）
  - 学年判定は `state.grade` で行う（`gradeMax` 不可。学年を戻す機能があるため）

### ⑤ 漢字497字の入力 — 決定

信頼できる教育漢字オープンデータを取り込み、学年別配当表との完全一致をスクリプトで検証する。読み・語例・熟語は人手レビューする。自動生成しただけで完了にしない。

### ⑥ ファイル分割 — 決定

`content/numbers/`、`content/reading/` 等へ分割し、互換用indexを置いて既存importパスを維持する。一度に全面移動せず、教科単位でテストしながら進める。

### ⑦ 進級と学習量 — 決定

1日約15分、1タスク4〜5問の基本枠は維持する。教材件数の増加をそのまま1日の必須問題数や進級条件数へ反映しない。全単元は学習対象にするが、単元内の複数項目経験・初回正解・別日学習で習得を判定する。追加前後の進級所要日数をシミュレーションし、意図しない急増があれば単元粒度を調整する。

### ⑧ 週間配分 — 決定

週間ミッションは問題バンク件数ではなく、学年別の教科学習バランスから決める。社会28問・英語12問のような固定偏重を避け、4週間のローリング集計で特定教科が長期間出ない状態を検出する。

### ⑨ 新規教材の到達性 — 決定

新規教材は登録だけで完了にしない。未出knowledgeIdを優先し、指定復習・期限到来SRS・誤答補強との順序を明文化する。小4〜6英語、追加漢字、理社の新単元が実際に出題されることを固定seedテストで確認する。

### ⑩ 完了の定義 — 決定

各WPは、データ追加、生成テスト、保存・復習キー整合、未出到達性、解説表示、進級影響、実機導線、最新mainへの反映、GitHub Pages公開確認まで終えて完了とする。実機でしか判断できない項目は完了扱いにせず「要実機確認」と記録する。
